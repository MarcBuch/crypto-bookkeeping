How the Web App Fetches LP Positions and P&L Data

This page documents the actual runtime path used by the web application to load, refresh, cache, and display ProjectX LP position and P&L data.

Frontend

React + React Query fetches cached LP and P&L views from the API and merges them in the browser by tokenId.

API

Fastify exposes read endpoints for cached data and write endpoints that trigger async background sync jobs.

Core

Shared services fetch on-chain position state, resolve lifecycle events, price tokens, compute LP economics, and persist normalized view caches.

Storage

SQLite is the read path for the dashboard. The web app does not hit chain RPCs or CoinGecko directly.

Primary Runtime Flow

  1. The dashboard mounts in apps/web/src/App.tsx and calls useDashboardPositions().
  2. useDashboardPositions() in apps/web/src/hooks/useDashboardPositions.ts runs a React Query useQuery with getDashboardPositions.
  3. getDashboardPositions() in apps/web/src/api.ts performs Promise.all([getPositions(), getPnL()]).
  4. GET /positions and GET /pnl return cached JSON views from SQLite through Fastify route handlers.
  5. The browser merges both result sets by tokenId, producing DashboardPosition objects.
  6. The UI renders position cards and portfolio totals, and applies a few display-only calculations such as carry run rate and current balance in USD.

Key Point

The dashboard is intentionally cache-backed. Normal page loads read from positions_view_cache and pnl_view_cache. Live chain reads only happen during explicit sync operations or selected auxiliary endpoints such as IL.

Sync and Cache Refresh Flow

The dashboard does not continuously poll LP positions. Refresh is user-driven. Clicking Sync starts a background server job, then the client polls sync status every 2 seconds until the job completes or fails.

Where Position Data Comes From

  1. syncLpData(config) in packages/core/src/services/positions.ts starts by enumerating on-chain positions with getAllPositions().
  2. getPositionsView() projects each raw position into a normalized PositionView using lifecycle-aware current-state projection.
  3. The resulting view contains the current token balances, price range, current price, range status, and whether the position is currently in range.
  4. The API route GET /positions later reads these materialized views from positions_view_cache.

Where P&L Data Comes From

  1. During the same sync, getPnLView(config) computes a materialized PnLView per position.
  2. It resolves entry and close lifecycle facts, then calls calculateLpEconomics(facts).
  3. It enriches the result with USD prices. Active positions use live USD prices. Closed positions prefer persisted close-time USD prices and fall back to historical CoinGecko pricing when needed.
  4. The API route GET /pnl reads these materialized views from pnl_view_cache. It may lazily backfill a missing openedAt timestamp from the stored entry block.

Calculation Ownership

Computed in Core Before Caching

  • entryAmount0, entryAmount1, exitAmount0, exitAmount1
  • feesCollected0, feesCollected1, pendingFeesValueInToken1
  • absolutePnlInToken1, absolutePnlPercent
  • divergenceLossPercent
  • opportunityCostInToken1
  • netVsHodlPercent
  • feesValueUsd and per-token USD fee values when prices are available

Computed in the Web UI After Fetch

  • currentBalanceUsd(position) in apps/web/src/App.tsx
  • calculateThirtyDayPortfolioCarryRunRate(positions)
  • buildBlotterPnl(...), which combines LP P&L with hedge P&L for display
  • Portfolio totals such as total mark-to-market P&L and lifetime fee income

Loading and Error Behavior

  • fetchJson() throws ApiError on non-2xx responses.
  • App.tsx renders explicit loading and error states for the dashboard query.
  • Sync UI separately shows in-progress, complete, and failed banners.
  • GET /positions/:tokenId and GET /positions/:tokenId/pnl return 400 for invalid token IDs and 404 for missing positions.
  • P&L USD enrichment is optional; token1-denominated economics can still render when USD prices are unavailable.

Refresh Semantics

  • useDashboardPositions() does not define periodic refetch polling.
  • Full sync polling interval: 2000ms via useSyncPositions().
  • Per-position sync polling interval: 2000ms via useSyncPosition(tokenId).
  • After sync completion, the client invalidates the dashboardPositions query and refetches cached data.
  • This design keeps normal dashboard reads fast and protects chain and pricing dependencies from every page load.

Configuration That Influences Fetching

The API loads a shared tracker config, which controls how the sync job discovers lifecycle events and prices assets.

positions[tokenId].openTx and closeTx

Provide known lifecycle transactions for faster and more reliable entry/close discovery.

pricing.coingeckoIds

Maps token symbols or addresses to CoinGecko IDs for USD pricing and historical close valuation.

rpc and logsRpc

Define where core services read contracts, logs, receipts, and blocks during sync.

logsFromBlock

Limits how far back event discovery scans when the lifecycle is not fully specified in config.

Summary

The web app reads two precomputed cache-backed views, PositionView and PnLView, from the Fastify API. Those views are generated during explicit sync jobs in the shared core package, which pull on-chain state, resolve lifecycle events, fetch USD pricing, compute LP economics, and persist the result in SQLite. The browser merges the two datasets by tokenId and applies only a small amount of presentation-level aggregation afterward.
