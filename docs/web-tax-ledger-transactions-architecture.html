How the Web Tax Ledger Fetches Transactions

This page documents the actual runtime path used by the tax ledger UI to load, paginate, filter, sync, and edit tax transactions.

Frontend

The /tax route loads paginated transactions with React Query and renders a client-side grouped table.

API

Fastify serves live transaction rows from SQLite and exposes sync, manual create, and update endpoints.

Core

Core services import transactions from HyperSync, explorer fallbacks, LP flow synthesis, hedge flow synthesis, and EUR enrichment.

Storage

The ledger read path is live against the tax_transactions SQLite table. There is no separate server-side view cache for list reads.

Primary Runtime Flow

  1. The router maps /tax to apps/web/src/TaxTransactions.tsx.
  2. TaxTransactions calls useTaxTransactions({ limit, offset, label }).
  3. useTaxTransactions() in apps/web/src/hooks/useTaxTransactions.ts runs a React Query request whose query key includes the current pagination and filter options.
  4. getTaxTransactions() in apps/web/src/api.ts sends GET /tax/transactions?limit=&offset=&label=.
  5. The Fastify tax route validates query parameters, reads rows directly from SQLite, and returns { transactions, pagination }.
  6. The UI groups rows by hash and applies table sorting and expansion locally after the fetch completes.

Key Point

Unlike LP positions and P&L, tax ledger reads are not served from a materialized view cache. The list endpoint queries tax_transactions directly on every server request. The only cache on the read path is React Query in the browser.

Pagination and Filtering

Server-Side

  • listTaxTransactions(limit, offset, label) applies SQL LIMIT and OFFSET.
  • Rows are ordered by time_stamp DESC, block_number DESC.
  • countTaxTransactions(label) computes the total count for pagination.
  • label supports specific labels and an unlabeled mode via label IS NULL.

Client-Side

  • TaxTransactions.tsx owns page and rowsPerPage state.
  • Changing page or page size produces a new React Query key and refetch.
  • Transaction grouping by hash happens after fetch in buildTableRows().
  • TanStack Table sorting and row expansion are presentation concerns only.

Sync and Refresh Flow

Tax sync is explicit. The list endpoint does not trigger imports. The UI uses a mutation to run sync, then invalidates all tax transaction queries so the list refetches.

External Sources That Feed the Ledger

  • HyperSync transaction history via fetchTransactionsByAddress()
  • HyperSync token transfer history via fetchTokenTransfersByAddress()
  • Explorer API fallback for txlistinternal
  • LP lifecycle-derived synthetic tax rows from syncLpTaxFlows()
  • Hedge-derived synthetic tax rows from hedge tax flow sync
  • CoinGecko historical pricing for EUR cost/proceeds/gain enrichment

Incremental Sync State

  • getTaxSyncState(wallet) reads the last synced block watermark.
  • syncTaxTransactions() resumes from last_block_number + 1.
  • upsertTaxSyncState() records the new watermark and sync timestamp.
  • This avoids full history re-import on every sync.
The ledger is not rebuilt from scratch on every refresh. It is an incrementally updated, durable transaction table.

Manual Create and Update Flow

Manual Create

  • The UI submits POST /tax/transactions.
  • The API validates the editable manual fields.
  • createManualTaxTransaction() inserts a row with source = "manual" and transaction_type = "manual".
  • The new row appears in normal list reads immediately after query invalidation.

Manual Update

  • The UI submits PATCH /tax/transactions/:id.
  • updateTaxTransaction() allows full ledger-field edits only for manual rows.
  • For synced rows, label and comment remain editable, but core ledger properties are protected.
  • Successful updates invalidate all tax transaction queries and refetch the list.

Mutation and Query Behavior

Action Frontend hook Effect on data
List fetch useTaxTransactions() Fetches a specific limit/offset/label slice.
Sync import useSyncTaxTransactions() Runs backend sync, then invalidates all ["taxTransactions"] queries.
Create manual row useCreateTaxTransaction() Inserts a manual row, then invalidates all tax transaction queries.
Update row useUpdateTaxTransaction() Writes to SQLite, then invalidates all tax transaction queries.

Loading and Error Behavior

  • TaxLoadingState renders during initial query load.
  • TaxErrorState renders when the query fails.
  • TaxEmptyState renders when no rows are returned.
  • While the list is refetching, the UI shows Refreshing list....
  • Mutation failures for sync, create, and update are shown inline in the screen.

Write Protection Rules

  • upsertSyncedTaxTransaction() will not overwrite rows whose source is manual.
  • Manual-only ledger fields cannot be edited on synced rows.
  • This preserves user-entered corrections and manual bookkeeping records during later syncs.

Summary

The tax ledger UI fetches paginated transaction rows directly from SQLite through GET /tax/transactions. React Query caches those pages in the browser, while sync, manual create, and update mutations invalidate the cached lists and trigger refetches. The underlying ledger table is incrementally maintained by a core sync process that merges external blockchain activity, synthetic LP and hedge events, and historical EUR enrichment.
